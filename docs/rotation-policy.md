# 업무 분배 로테이션 MVP 정책

## 1. 문서 목적

이 문서는 Sharing Log의 일간·주간·격주 업무를 생성하고 담당자를 배정할 때 적용하는 MVP 정책을 정의한다. 구현체와 테스트는 이 문서를 기준으로 하며, 아래에서 `반드시`, `하지 않는다`로 표현한 규칙은 예외 없이 지켜야 한다.

MVP의 로테이션은 **완전 무작위 배정이 아니라 공정성을 우선한 무작위 배정**이다. 먼저 업무 가능 여부와 공정성 점수로 후보를 좁히고, 모든 조건이 같은 후보가 둘 이상일 때만 무작위로 한 명을 선택한다.

## 2. 핵심 용어

- **업무 정의(Chore)**: 업무명, 반복 주기, 가능 멤버, 격주 기준일 등 반복되는 업무의 설정이다.
- **회차(Occurrence)**: 특정 기간에 실제로 수행해야 하는 업무 한 건이다. 같은 업무라도 매일·매주·격주마다 별도 회차가 만들어진다.
- **배정 시도(Assignment Attempt)**: 한 회차가 한 멤버에게 배정되었다가 완료, 탈퇴, 참여 변경, 대타 수락 등의 사유로 끝날 때까지의 기록이다. 재배정할 때 기존 기록을 덮어쓰지 않고 새 배정 시도를 추가한다.
- **활성 멤버(Active Member)**: 그룹을 탈퇴하지 않아 현재 업무를 배정받을 수 있는 멤버다.
- **가능 멤버(Eligible Member)**: 해당 업무를 수행할 수 있도록 설정된 멤버다.
- **대타 요청(Substitute Request)**: 현재 담당자를 유지한 채 회차의 다른 가능 멤버들에게 대타 수락을 요청하는 별도 워크플로다.
- **유효 완료(Effective Completion)**: 완료 취소되지 않은 실제 완료 기록이다. 공정성 집계에는 유효 완료만 반영한다.
- **공정성 점수**: 후보 간 우선순위를 정하기 위해 계산하는 비교 값이다. 값이 작은 후보가 먼저 선택된다.

## 3. MVP 정책 결정

| 상황 | MVP 정책 |
|---|---|
| 특정 사람만 할 수 있는 업무 | 활성 멤버 중 업무의 가능 멤버로 등록된 사람만 후보가 된다. 가능 멤버 제한이 없으면 모든 활성 멤버가 후보가 된다. |
| 현재 담당자가 그룹을 탈퇴 | 아직 종료되지 않은 회차만 즉시 자동 재배정한다. 완료되거나 생략된 과거 회차와 배정 이력은 변경하지 않는다. |
| 재배정 가능한 후보가 없음 | 가능 멤버 제한이나 수행 불가 결정을 무시하지 않고 회차를 `NEEDS_ATTENTION`으로 전환한다. |
| 후보가 여러 명 | 공정성 규칙으로 후보를 좁힌 뒤 최종 동점자 사이에서만 무작위로 선택한다. |
| 담당자가 `대타 요청`을 선택 | 현재 담당자를 유지한 채 다른 가능 멤버에게 요청한다. 첫 수락자가 담당자가 되며 이는 선택 순서나 자동 랜덤 배정이 아닌 명시적 수락이다. |
| 완료자가 `완료 취소`를 선택 | 완료 기록은 삭제하지 않고 취소 메타데이터를 남긴 뒤 같은 멤버에게 회차를 다시 배정한다. |

현재 담당자에게 공개하는 회차 행동은 `업무 완료`와 `대타 요청`이다.
`SKIPPED`, `SKIPPED_ALREADY_DONE`, `DECLINED_BY_ASSIGNEE`,
`DECLINE_REASSIGNMENT`는 기존 데이터와 진행 중인 레거시 회차의 감사 이력을
보존하기 위한 값이며, 새 버튼이나 공개 API에서 생성하지 않는다.

## 4. 가능 멤버 정책

1. 업무마다 가능 멤버 제한을 둘 수 있다.
2. 가능 멤버 제한이 없는 업무는 현재 그룹의 모든 활성 멤버가 수행할 수 있다.
3. 가능 멤버 제한이 있는 업무는 다음 조건을 모두 만족하는 멤버만 후보가 된다.
   - 현재 그룹의 활성 멤버다.
   - 해당 업무의 가능 멤버 목록에 포함되어 있다.
   - 레거시 수행 불가 이력이 있는 회차라면 해당 회차에서 제외된 적이 없다.
   - 자동 최초·재배정 후보라면 해당 회차의 대타 수락으로 이전 담당에서 빠진 멤버가 아니다. 단, 새 담당자가 다시 대타를 요청할 때는 이전 담당자도 요청 수신자가 될 수 있다.
4. 탈퇴 멤버는 가능 멤버 목록에 남아 있더라도 후보가 될 수 없다.
5. 후보가 없더라도 레거시 수행 불가 멤버나 가능 멤버가 아닌 사람을 임의로 후보에 다시 넣지 않는다.
6. 업무 설정 변경은 기본적으로 다음에 생성되는 회차부터 적용한다. 이미 생성된 회차에는 생성 시점의 업무 설정 스냅샷을 사용하며, 담당자의 탈퇴만 현재 회차에 즉시 반영한다.
7. 단, `NEEDS_ATTENTION` 회차를 복구할 때 관리자가 `현재 회차에도 적용`을 명시적으로 선택하면 변경된 가능 멤버 조건을 그 회차의 스냅샷에 새 버전으로 기록한 뒤 재배정할 수 있다. 기존 스냅샷과 변경 이력은 삭제하지 않는다.

## 5. 회차 상태 머신

### 5.1 회차 상태

| 상태 | 의미 | 담당자 표시 |
|---|---|---|
| `ASSIGNED` | 유효한 담당자가 배정되어 수행을 기다리는 상태 | 반드시 1명 |
| `COMPLETED` | 담당자가 실제로 업무를 완료한 종료 상태 | 종료된 배정 이력의 마지막 담당자 |
| `SKIPPED` | 과거 버전에서 생략된 레거시 종료 상태 | 종료된 배정 이력의 마지막 담당자 |
| `NEEDS_ATTENTION` | 유효한 후보가 없어 자동 배정할 수 없는 상태 | 없음 |

회차 생성과 최초 배정은 한 작업으로 처리한다. 후보가 있으면 곧바로 `ASSIGNED`, 후보가 없으면 `NEEDS_ATTENTION`으로 저장하므로 별도의 장기 `PENDING` 상태를 두지 않는다.

`현재 담당자`는 활성 배정 시도의 담당자를 뜻한다. 종료 상태에서는 현재 담당자를 비우고, 화면에 필요한 마지막 담당자는 종료된 배정 이력에서 조회한다.

### 5.2 허용되는 상태 전이

```text
회차 생성 ── 후보 있음 ───────────────> ASSIGNED
        └─ 후보 없음 ───────────────> NEEDS_ATTENTION

ASSIGNED ── 실제 완료 ───────────────> COMPLETED
ASSIGNED ── 담당자 탈퇴 ─────────────> 재배정
ASSIGNED ── 대타 수락 ───────────────> ASSIGNED(수락자로 담당 변경)

재배정 ── 후보 있음 ─────────────────> ASSIGNED
      └─ 후보 없음 ─────────────────> NEEDS_ATTENTION

NEEDS_ATTENTION ── 후보 조건 보완 후 재시도 성공 ──> ASSIGNED
NEEDS_ATTENTION ── 재시도해도 후보 없음 ──────────> NEEDS_ATTENTION
COMPLETED ── 마지막 유효 완료자가 완료 취소 ──────> ASSIGNED
```

기존 `SKIPPED` 이력은 되돌리지 않는다. `COMPLETED`는 마지막 유효 완료자만 완료 취소하여 다시 `ASSIGNED`로 열 수 있다. 대타 요청의 상태는 회차 상태와 별개이며, 요청 대기·거절·소진 중에도 회차는 원 담당자의 `ASSIGNED` 상태를 유지한다.

### 5.3 배정 시도 종료 사유

재배정과 감사 이력을 구분하기 위해 배정 시도에는 최소한 다음 종료 사유를 기록한다.

- `COMPLETED`: 실제 수행 완료
- `SKIPPED_ALREADY_DONE`: 과거 버전에서 생략된 레거시 종료 사유
- `DECLINED_BY_ASSIGNEE`: 과거 버전에서 수행 불가를 선택한 레거시 종료 사유
- `ASSIGNEE_LEFT_GROUP`: 담당자가 그룹에서 탈퇴
- `PARTICIPATION_REMOVED`: 현재 회차 참여 대상에서 제외
- `SUBSTITUTE_ACCEPTED`: 다른 멤버가 대타 요청을 수락

새 배정 계기는 최초·탈퇴·참여 변경·관리자 재시도 외에 `SUBSTITUTE_ACCEPTANCE`, `COMPLETION_REOPENED`를 기록한다. 기존 `DECLINE_REASSIGNMENT` 값은 과거 이력 호환을 위해 유지한다.

배정 시도의 핵심 기록은 삭제하거나 덮어쓰지 않는다. 재배정할 때 기존 활성 배정 시도를 종료하고 새로운 배정 시도를 생성한다. 완료 취소는 기존 완료 배정에 취소 시각·취소자·메모를 추가해 감사 이력을 보존한다.

## 6. 사용자 행동별 처리

### 6.1 실제로 완료했어요

1. `ASSIGNED` 상태의 현재 담당자만 완료할 수 있다.
2. 회차를 `COMPLETED`로 종료한다.
3. 현재 배정 시도를 `COMPLETED` 사유로 종료한다.
4. 해당 담당자에게 이 업무의 완료 횟수 1회를 반영한다.
5. 같은 요청이 중복 도착해도 완료 기록과 점수는 한 번만 반영한다.

### 6.2 대타를 요청했어요

1. `ASSIGNED` 상태의 현재 담당자만 사유와 함께 요청할 수 있다.
2. 요청 생성만으로 담당자나 회차 상태는 바뀌지 않는다.
3. 요청 수신자는 회차 스냅샷의 현재 활성 가능 멤버에서 요청자와 같은 회차의 레거시 수행 불가 멤버를 뺀 사람들이다. 과거에 이 회차의 대타 수락으로 담당에서 빠진 멤버도 새 담당자의 다음 대타 요청에는 다시 수신자가 될 수 있다.
4. 다른 멤버의 요청이 진행 중일 때는 같은 회차에 새 요청을 만들 수 없고 `다른 사용자가 올린 대타 요청입니다`라고 안내한다.
5. 첫 유효 수락자가 새 담당자가 된다. 기존 배정은 `SUBSTITUTE_ACCEPTED`로 종료하고 새 배정은 `SUBSTITUTE_ACCEPTANCE`로 기록한다.
6. 한 명이 수락하면 다른 수신자는 `INELIGIBLE`이 된다. 거절한 수신자만 `DECLINED`가 되며, 전원이 거절·제외되면 요청은 `EXHAUSTED`가 된다.
7. 원 담당자가 완료 처리하거나 담당 자격을 잃으면 진행 중 요청은 `CANCELLED`가 된다.
8. 대타 수락은 수락자의 명시적 행동이므로 공정 랜덤 엔진을 다시 실행하지 않는다. 같은 회차의 현재 담당자만 교체하며 이미 생성된 다른 회차와 로테이션 계획은 변경하지 않는다.

### 6.3 완료를 취소했어요

1. `COMPLETED` 회차를 마지막으로 유효하게 완료한 현재 활성 멤버만 취소할 수 있다.
2. 기존 완료 배정은 삭제하지 않고 취소 시각·취소자·메모를 기록한다.
3. 회차를 `ASSIGNED`로 열고 같은 멤버에게 `COMPLETION_REOPENED` 배정을 새로 만든다.
4. 취소된 완료는 업무 완료 횟수와 현재 기간 업무량에서 제외한다.
5. 기존 `SKIPPED` 회차는 레거시 이력으로 유지하며 취소할 수 없다.

### 6.4 담당자가 탈퇴했어요

1. 멤버를 탈퇴 상태로 바꿀 때 그 멤버가 현재 담당자인 모든 미종료 회차를 찾는다.
2. 각 활성 배정 시도를 `ASSIGNEE_LEFT_GROUP` 사유로 종료한다.
3. 해당 탈퇴 멤버를 제외하고 각 회차를 자동 재배정한다.
4. 후보가 없으면 해당 회차를 `NEEDS_ATTENTION`으로 전환한다.
5. `COMPLETED` 또는 `SKIPPED` 상태인 과거 회차는 재배정하지 않는다.
6. 탈퇴 멤버의 과거 배정·완료·생략 이력은 삭제하거나 다른 멤버에게 이전하지 않는다.

### 6.5 자동 배정할 사람이 없어요

1. 회차 상태는 `NEEDS_ATTENTION`이고 현재 담당자는 없다.
2. 시스템은 가능 멤버 제한이나 레거시 수행 불가 기록을 자동으로 완화하지 않는다.
3. 관리자는 가능 멤버 설정 또는 멤버 상태를 바로잡은 뒤 재배정을 다시 실행할 수 있다. 가능 멤버 변경을 현재 회차에 적용하려면 `현재 회차에도 적용`을 명시적으로 선택해야 하며, 그 변경은 감사 이력으로 남긴다.
4. 재시도 시에도 같은 후보 필터와 공정 배정 규칙을 적용한다.

## 7. 일간·주간·격주 기간 규칙

### 7.1 공통 규칙

1. 모든 날짜 경계는 그룹의 시간대(`timeZone`)를 기준으로 계산한다.
2. 시간대가 아직 설정되지 않은 기존 그룹은 `Asia/Seoul`을 기본값으로 사용한다.
3. 기간은 시작을 포함하고 끝을 포함하지 않는 반개구간 `[periodStart, periodEnd)`으로 표현한다.
4. 기간 경계는 현지 달력 날짜로 먼저 계산한 뒤 시각으로 변환한다. 하루를 고정 24시간으로 계산하지 않는다.
5. 같은 업무·일정 개정·기간 시작일에는 회차를 하나만 생성한다. 스케줄러나 API가 여러 번 실행되어도 같은 일정 개정의 중복 회차가 생기지 않아야 한다.
6. 회차에는 일정 개정 번호와 생성 당시 업무명, 반복 주기, 기간, 가능 멤버 조건을 스냅샷으로 보존한다. 현재 회차 화면은 업무 정의의 최신 이름을 표시하고, 완료 이력은 회차 생성 당시 이름 스냅샷을 표시한다.
7. 업무 일정이 실제로 변경되면 일정 개정 번호를 증가시킨다. 변경 시점의 현지 날짜에 활성인 미종료 회차가 있으면 담당자와 상태를 유지한 채 그 회차의 주기·기간·마감 시각 스냅샷을 새 개정으로 즉시 변경한다.
8. 활성 미종료 회차가 없으면 완료 이력을 변경하거나 일정 수정 처리 중 새 회차를 만들지 않는다. 다음 회차 생성 시 새 일정 개정을 사용한다.

### 7.2 일간(`DAILY`)

- `periodStart`: 그룹 시간대의 해당 날짜 00:00
- `periodEnd`: 다음 현지 날짜 00:00
- 예: 2026-07-23 일간 회차는 `[2026-07-23 00:00, 2026-07-24 00:00)`이다.

### 7.3 주간(`WEEKLY`)

- 그룹마다 주 시작 요일(`weekStartDay`)을 갖는다.
- 기본 주 시작 요일은 월요일이다.
- `periodStart`: 조회 날짜가 속한 주의 시작 요일 00:00
- `periodEnd`: `periodStart`에서 현지 달력 기준 7일 뒤 00:00
- 예: 주 시작 요일이 월요일이면 2026-07-23이 속한 회차는 `[2026-07-20 00:00, 2026-07-27 00:00)`이다.

### 7.4 격주(`BIWEEKLY`)

- 격주 업무마다 기준 시작일(`anchorDate`)이 반드시 있어야 한다.
- `anchorDate`는 해당 업무의 첫 격주 기간 시작일이며, 그룹의 주 시작 요일과 같아야 한다.
- 각 격주 기간은 `anchorDate + 14 × n일`에 시작하고 현지 달력 기준 14일 동안 유지된다.
- 임의 날짜가 속한 기간은 `anchorDate`와의 날짜 차이를 14로 내림 나눗셈하여 계산한다.
- `periodStart`: `anchorDate + 14 × floor(daysBetween(anchorDate, targetDate) / 14)일`
- `periodEnd`: `periodStart`에서 현지 달력 기준 14일 뒤 00:00
- 예: 기준 시작일이 2026-07-13이면 2026-07-23이 속한 회차는 `[2026-07-13 00:00, 2026-07-27 00:00)`이다.

UI의 `매일`, `매주`, `격주` 섹션은 각각 현재 현지 시각을 포함하는 회차를 조회해 표시한다.

## 8. 공정 배정 규칙

### 8.1 여러 회차를 한 번에 배정하는 순서

같은 시점에 여러 회차를 생성하거나 재배정해야 하면 **현재 유효 후보 수가 적은 업무부터** 처리한다. 제한 업무를 먼저 배정해야 제한이 없는 업무가 희소한 후보를 먼저 가져가는 일을 줄일 수 있다. 후보 수가 같으면 업무 ID, 회차 ID 순서로 처리하여 실행 순서를 재현할 수 있게 한다.

### 8.2 후보 필터

각 회차의 후보 집합은 다음 교집합이다.

```text
현재 활성 그룹 멤버
∩ 회차 생성 시점의 가능 멤버
− 이 회차의 레거시 수행 불가 이력으로 제외된 멤버
```

재배정 시에는 탈퇴한 현재 담당자도 반드시 제외한다. 필터 결과가 비어 있으면 무작위 선택을 시도하지 않고 `NEEDS_ATTENTION`으로 전환한다.

### 8.3 후보 우선순위

후보마다 다음 값을 순서대로 비교한다. 앞 항목이 같을 때만 다음 항목을 비교하며, 값이 작은 후보를 우선한다.

1. **같은 주기·현재 기간의 업무량**
   - 대상 회차와 반복 주기 및 기간 시작일이 같은 회차 중, 후보의 유효 할당 수가 작은 멤버를 우선한다.
   - 새 업무를 만들 때 이미 생성된 같은 주기·같은 기간의 배정 기록을 확인하므로, 아직 그 기간에 배정되지 않은 멤버부터 선택한다.
   - 가능 멤버 수보다 업무 수가 많아 중복이 불가피하면 해당 회차의 가능 후보 중 기간 내 배정 횟수가 가장 적은 멤버부터 다시 선택해 업무량 편차를 최소화한다.
2. **해당 업무의 1사이클 진행도**
   - `해당 업무의 과거 유효 할당 횟수 + 공정성 크레딧`이 가장 작은 멤버를 우선한다.
   - 유효 할당은 아직 활성인 배정 시도 또는 완료 취소되지 않은 `COMPLETED` 배정 시도다. 수행 불가, 탈퇴, 참여 제외, 대타 수락, 계획 재생성 등으로 무효화된 배정 시도는 포함하지 않는다.
   - 같은 기간 업무량이 같은 후보 안에서는 업무 참여자가 가능한 한 한 번씩 배정된 뒤 다음 사이클을 시작한다.
   - 새로 추가되거나 재합류한 멤버에게는 가입 시점까지 계산한 기존 참여자의 최대 진행도보다 1 큰 값이 되도록 크레딧을 부여한다. 같은 기간 업무량이 같으면 기존 참여자의 현재 사이클을 우선하며, 후발 멤버가 이번 기간의 중복 배정을 피할 유일한 후보라면 기간 분산을 우선한다.
3. **같은 카테고리의 과거 유효 할당 횟수**
   - 현재 도메인에서 카테고리는 반복 주기(`DAILY`, `WEEKLY`, `BIWEEKLY`)를 뜻한다.
   - 대상 회차보다 기간 시작일이 이른 같은 반복 주기 회차 중, 후보가 가진 유효 할당 수가 작은 멤버를 우선한다.
   - 일정이 변경된 과거 업무는 당시 회차에 저장된 반복 주기 스냅샷을 기준으로 집계한다.
4. **직전 회차 담당 여부**
   - 해당 업무의 직전 회차에서 마지막 담당자였으면 1, 아니면 0이다.
   - 다른 조건이 같다면 직전 담당자를 후순위로 둔다.
5. **무작위 동점 해소**
   - 1~4의 값이 모두 같은 후보 사이에서만 균등 무작위로 한 명을 선택한다.

즉, 후보의 비교 키는 다음과 같다.

```text
(현재 기간 업무량, 업무별 유효 할당 횟수 + 크레딧,
 같은 주기 과거 유효 할당 횟수, 직전 담당 여부, 무작위 동점 값)
```

멤버가 재합류하면 활성 세대가 증가한다. 회차의 가능 멤버 스냅샷에는 당시 활성 세대를 함께 저장하므로, 탈퇴 전에 만들어진 회차에는 재합류한 멤버가 다시 후보로 들어가지 않는다. 수동으로 업무에서 제외한 멤버는 재합류만으로 자동 복구하지 않는다.

자동 최초·재배정은 위 공정 점수로 후보를 좁힌 뒤 최종 동점자 사이에서만 무작위 선택한다. 대타 수락과 완료 취소 복원은 사용자가 담당자를 명시한 행동이므로 예외적으로 직접 배정하며, 결정 이력에는 `manual-action-v1`과 seed `0`을 남긴다.

무작위 결과를 다시 설명하고 테스트할 수 있도록 배정 결정마다 다음 정보를 보존한다.

- 배정 알고리즘 버전
- 선택 당시 후보 목록
- 제외된 멤버와 제외 사유
- 후보별 공정성 비교 값
- 최종 동점 해소에 사용한 seed 또는 동등한 재현 정보
- 최종 선택 멤버

## 9. 불변조건

다음 조건은 모든 API, 스케줄러, 탈퇴 처리, 재시도 경로에서 항상 성립해야 한다.

1. `(업무 ID, 기간 시작일)` 조합당 회차는 최대 하나다.
2. 한 회차에는 활성 배정 시도가 최대 하나다.
3. `ASSIGNED` 회차는 현재 담당자와 활성 배정 시도를 정확히 하나씩 가진다.
4. `NEEDS_ATTENTION` 회차는 현재 담당자와 활성 배정 시도를 가지지 않는다.
5. 현재 `COMPLETED`와 `SKIPPED` 회차는 현재 담당자와 활성 배정 시도를 가지지 않는다. 마지막 담당자는 종료된 배정 이력으로만 보존한다.
6. 현재 담당자는 반드시 현재 그룹의 활성 멤버이며 해당 회차의 가능 멤버다.
7. 레거시 수행 불가 이력이 있는 멤버는 그 회차에 다시 배정되지 않는다.
8. 활성 배정 시도와 취소되지 않은 유효 `COMPLETED`만 유효 할당 횟수에 반영한다. 레거시 `SKIPPED`, 취소된 완료와 종료 사유가 있는 무효 배정은 어떤 공정성 점수에도 반영하지 않는다.
9. 담당자 변경은 기존 배정 시도를 덮어쓰지 않고 종료 사유를 남긴 뒤 새 배정 시도를 추가하는 방식으로만 수행한다.
10. 탈퇴는 과거 회차, 점수, 배정 이력을 삭제하거나 다른 멤버 소유로 변경하지 않는다.
11. 후보가 없을 때 가능 멤버 제한이나 레거시 수행 불가 결정을 자동으로 무시하지 않는다.
12. 동일한 완료·탈퇴 이벤트가 중복 전달되어도 상태 전이와 점수 반영은 한 번만 일어난다.
13. 동시에 여러 요청이 들어와도 하나의 회차에 두 명의 현재 담당자가 생기지 않는다.
14. `COMPLETED`는 마지막 유효 완료자만 다시 열 수 있고, `SKIPPED`는 다시 열리지 않는다.
15. 모든 날짜 계산은 회차에 기록된 그룹 시간대와 현지 달력 규칙을 사용한다.
16. 한 회차에는 진행 중 대타 요청이 최대 하나이고, 한 요청에는 수락자가 최대 한 명이다.
17. 대타 수락도 기존 배정을 덮어쓰지 않고 종료한 뒤 새 배정을 추가한다.

## 10. MVP에서 제외하는 범위

다음 기능은 핵심 자동 로테이션이 안정된 이후 별도 정책으로 설계한다.

- 멤버 투표로 대타 선정
- 멤버 간 직접 교환 또는 담당권 양도
- 휴가·외출·요일별 가능 시간 등 사전 가용성 캘린더
- 업무 난이도, 예상 소요 시간, 선호도에 따른 가중치
- 사진·위치 등 완료 증빙과 관리자 승인
- 포인트, 벌점, 보상, 연속 수행 보너스
- `SKIPPED` 결과 취소 또는 과거 완료자의 임의 변경
- 관리자가 가능 멤버 정책을 무시하는 강제 배정
- 과거 업무 설정 변경에 따른 회차 재생성·소급 재배정

## 11. 필수 인수 시나리오

구현 완료 여부는 최소한 다음 시나리오로 검증한다.

1. 제한 업무는 지정된 활성 멤버에게만 배정된다.
2. 미완료 회차의 담당자가 탈퇴하면 자동 재배정되고, 후보가 없으면 `NEEDS_ATTENTION`이 된다.
3. 완료된 회차의 담당자가 나중에 탈퇴해도 해당 회차와 이력은 바뀌지 않는다.
4. 같은 생성 작업을 반복 실행해도 동일 업무·기간의 회차가 중복 생성되지 않는다.
5. 동일 완료 요청을 동시에 여러 번 보내도 완료 횟수는 한 번만 증가한다.
6. 공정성 비교 값이 다른 후보 중에는 더 우선인 후보가 항상 선택되고, 완전히 같은 후보 사이에서만 무작위 선택이 일어난다.
7. 일간·주간·격주 경계 시각과 격주 기준일 전후의 기간 계산이 그룹 시간대 기준으로 정확하다.
8. 나노초 정밀도의 같은 생성·최초 결정 시각이 데이터베이스에서 마이크로초로 반올림되어도 세 주기 모두 회차 생성에 성공한다.
9. 대타 요청 중에는 원 담당자를 유지하고, 첫 수락 때만 수락자에게 담당자가 이전되며 나머지 수신자는 응답할 수 없게 된다.
10. 전원이 대타 요청을 거절해도 원 담당자는 유지되고 요청만 `EXHAUSTED`가 된다.
11. 완료 취소 시 같은 완료자에게 회차가 복원되고 취소된 완료는 공정성 집계에서 빠진다.
12. 완료 취소 후 다시 완료해도 유효 완료 횟수는 한 번만 반영된다.
13. 업무명·일정 수정은 기존 회차의 이름·일정 스냅샷을 바꾸지 않는다. 현재 회차는 최신 업무명을, 완료 이력은 스냅샷 이름을 표시한다.
14. 현재 담당자의 공개 행동에는 `업무 완료`와 `대타 요청`만 나타난다.
